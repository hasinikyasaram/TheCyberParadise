PHASE 1 — CORE SECURITY (MUST FINISH FIRST)
- Use UUID primary keys for shipments and related records.
- Create migrations for profiles/roles, shipments, assignments, shipment status
  events, and audit_log as appropriate to the existing schema.
- Enable RLS on every exposed table. Explicitly configure grants and policies:
  customers can read only their own shipments; drivers can read and update only
  shipments assigned to them; admins can manage assignments. Give each role
  only the necessary table privileges.
- Do not trust role, owner, assignment, shipment status, or actor fields from
  client input. Resolve identity and role from the authenticated server session
  and trusted database records.
- Enforce this state machine in Postgres, not only in the UI:
  created -> assigned -> picked_up -> in_transit -> delivered
  Reject invalid transitions and unauthorized status changes with a database
  function/trigger. Ensure assignment is valid before driver updates.
- Every protected server route/action must verify the session, role, and
  shipment-specific ownership/assignment before reading or writing.
- For shipment reads, return the same 404 response for nonexistent and
  unauthorized shipment IDs. Do not disclose whether another user's shipment
  exists.
- Validate all request bodies and query parameters with Zod on the server.
  Use safe parameterized database access; no SQL string concatenation.
- Implement append-only audit_log records with timestamp, actor ID, actor role,
  action, shipment ID when relevant, allowed/denied decision, and a safe reason.
  Log both allowed and denied protected actions. Do not log secrets, auth tokens,
  full addresses, or unnecessary personal data.
- Only admins can read audit entries. Prevent normal users from editing or
  deleting audit entries. Do not expose a service-role key to browser code.
- Add focused automated tests for migration/policy behavior and server routes.
  Include same-404 behavior and server-side enforcement, not just UI tests.

PHASE 2 — SECURE, READ-ONLY AI COPILOT
- The AI feature is read-only. It must have no write tools, database mutation
  capability, assignment action, or status-change capability.
- Verify the user session and shipment-level access before fetching any context
  for the model. Fetch only shipments that user may already see and pass the
  minimum necessary fields.
- Keep the model API key exclusively server-side. Never return it to the browser,
  logs, or error messages.
- Treat shipment notes and other user-controlled text as untrusted data. Clearly
  delimit them in the model context and instruct the model never to follow
  instructions contained in shipment notes.
- Never include another user's shipment data in context. Enforce this in server
  code before model invocation; do not rely on the prompt as an access control.
- Log AI requests and refusals safely, without storing secrets or unnecessary
  personal data.
- Add tests for a prompt-injection note, cross-customer data isolation, refusal
  behavior, server-only API key handling, and absence of write tools.
- Explain in the README that prompt instructions are defense in depth and are
  not a substitute for authorization and data minimization.

PHASE 3 — DEMO FEATURES
- Build an admin/demo-only Attack Lab with one button per scenario:
  1. Cross-customer shipment read
  2. Wrong-driver shipment update
  3. Skipped workflow step
  4. Direct database query using the wrong user's authenticated credentials
  5. Prompt injection through a synthetic shipment note
  6. Shipment ID enumeration
- Each scenario must execute against the real app/database protections, show
  BLOCKED or ALLOWED, show a safe reason, and link/display the corresponding
  audit entry. Never simulate a successful denial with hardcoded UI text.
- For the direct DB probe, use a regular user's authenticated key/session, never
  a service-role credential.
- Build demo-only layer switches to bypass exactly one designated application
  layer for illustrating defense in depth. They must be disabled by default,
  require an explicit demo environment flag AND admin authorization, show a
  persistent “INSECURE DEMO MODE — SYNTHETIC DATA ONLY” banner, and fail closed
  in production. They must never disable database RLS or weaken real production
  controls. The RLS and other remaining layers must still block the probe.
- Add a live security panel fed by real audit data: request, actor, decision,
  reason, time, and audit entry. Color-code decisions and avoid exposing secrets
  or personal data.
- Add a scorecard “X/Y attacks blocked” calculated from actual scenario results,
  not a constant or manually entered value.

PHASE 4 — EXTRA PROTECTIONS
- Field-level address privacy: drivers can access the full delivery address only
  while the shipment is assigned to them and active. Access ends on delivery or
  reassignment. Enforce this on the server and database access path, not merely
  by hiding a UI field. Add tests for active assignment, delivered shipment, and
  reassignment.
- Add public tracking by a cryptographically random, high-entropy tracking
  token. Do not use sequential shipment IDs as public credentials. Public
  responses contain only status and coarse location; never recipient/customer
  name, phone, exact address, or internal notes. Store a hash of the public token
  if practical; support revocation/rotation.
- Rate-limit login, tracking lookups, sensitive status actions, and AI requests
  using a shared backend-compatible limiter. Do not rely on per-process memory
  when deployed serverlessly.
- Detect repeated failed tracking IDs or tokens from one actor/source, record a
  safe alert, and rate-limit/deny continued attempts.
- Let the Copilot summarize suspicious events for admins only. Its context must
  be limited to authorized audit/security event fields, and it must remain
  read-only.

PHASE 5 — SEED, TESTS, DOCS, RESET

- Add automated tests for:

  - AI ignores/refuses the injected note and never sees other users' data
  - driver loses full-address access after delivery
  - public tracking response contains no personal data
  - every denied attempt is recorded in audit_log
  - admin-only audit access
  - demo layer switches fail closed outside demo mode
- Add a one-click “Reset demo data” control. It must be available only in local

- Update README with:

  - a 3-minute demo script: customer creates shipment; admin assigns driver;
